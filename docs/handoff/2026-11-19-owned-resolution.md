# Owned native resolution evidence

`ToolCapability::RepairResolution` produces `resolution.json` and a separate
worker receipt through the existing deterministic worker, candidate ingestion,
native publication, retained acknowledgement and replay lifecycle. It adds no
cache engine, provider call, issue close, selection or scratch retirement.

```text
reel-workflow-native export-resolution-request BASELINE_RETAINED_REVIEW PLAN REPAIR REVISION REBUILD_BINDINGS CORRECTED_RETAINED_REVIEWS DECISION NEW_REQUEST --apply
```

The private `reel.workflow-resolution-job.v1` request freezes the original
baseline/corrected review bundles, repair controls and observed retained producer
contexts. Capture checks immutable profile pins, journal result/acknowledgement
identity and exact source snapshots. It does not grant custody or complete a job.
Machine profiles/locators remain private payload data, not authored Git records.

`Request::resources` enumerates every declared parent native payload (including
unused record streams), result artifact and worker receipt. Object aliases use
hash/length with an explicit custody-only media type; the original record/annex
leaf identity is independently checked by the original retained proofs. Content
deduplication is not used to substitute an original asset identity. All contexts
and the child must use the same explicitly declared native store and physical
pool. Original contexts, Git history and pinned verification tools must remain
available; missing history is an error, never a latest-context fallback.

The task selects the request as `control/resolution-request` and the baseline
plan as its distinct publication input. Every parent resource object is declared
as a native record stream, with its exact stream-to-annex-leaf binding included
in the source declaration. The SDK protects these streams even though they are
not selected logical inputs. The task has no auxiliary programs, parts or
`source_bindings`, a pinned native runtime and one required JSON output bounded
by 1 MiB. Native admission owns
durable claims for the full declared closure before dispatch. The logical
126-resource/512 MiB bound does not override the SDK's 128-change transaction or
16-actor limits; preview/admission may refuse earlier. There is no splitting or
automatic alternative store.

Production rechecks frozen contexts, source plan, input set and source bindings,
then recomputes the checked resolution with exact producer-derived review copies.
It requires live admitted or retained child authority. Captured control bytes
are hash-checked; their read gates are released before reopening parent proofs
while durable child fences remain held, avoiding reentrant payload gates when
control bytes are also parent inputs. Every protected resource stream is reopened
and hash/length-checked sequentially before parent proof replay; no duplicate
read gate remains held across those proofs.

The receipt and every output must equal deterministic replay before native
completion/history is accepted. `RetainedGuard::resolution_proposal()` returns
the checked typed proposal only from the live resolution proof. Deserializing
JSON or an acknowledgement cannot create that guard or grant approval.

The native fixture uses the existing corrected-comic lineage at `.tmpkHoGyv`,
admits a new owned resolution task, checks each resource's protection, dispatches
through the existing worker, retains/replays it and reopens the typed native proof.
It compares against the earlier qualified local proposal and preserves all three
parent claim files. The fixture's actual qualification results are recorded only
after execution; compilation alone does not establish lifecycle completion.

Rights/provenance and comics-editor checks preserve original evidence, exact
language/context, private metadata and technical/creative separation. No actual
viewing, creative approval, tracker effect or public release is implied. Retained
tracker delivery/close receipts and managed close scheduling remain separate work.

The first fixture represented each of 24 resource objects as its own selected
record. It refused with `admission-atomic-claim-bound` before acceptance, with
no receipt or native publication. Its root `.tmpHDjgoX` and source `.tmpgRbhWK`
are preserved. The revised fixture uses the existing declared-stream machinery
to represent exactly the same object closure with fewer record/metadata objects.
The 128-change limit remains intact; no split admission, omitted resource or new
cache is introduced. A new fixture is permitted because the original never
accepted a protection work/activation or published controls.

The stream-based second fixture admitted 68 declared objects and published its
two controls, then refused automatic dispatch with
`dispatch-qualified-tool-required`. The original runtime omitted
`RepairResolution` from two independent dispatch/worker capability lists, while
its producer, return verifier and retained proof already supported the capability.
The accepted job `.tmp4xlWag` and source `.tmpRWRuor` remain bound to runtime
`b8986dff2b407061c5ed1eebb79b25aed66b309d56d6d97d6a71cbb1b7b42fba`.
Its protection must not be discarded or its runtime silently replaced.

Dispatch and worker admission now share an exhaustive capability function. An
explicit ignored recovery fixture prepares a manual deterministic return for the
original task, then invokes its original pinned lifecycle executable to
independently recompute, import, retain and replay it. This is manual return
recovery, not evidence that the original automatic worker ran. It creates no new
admission and checks the original packet/profile/receipt and all three parent
claim files remain unchanged. Its actual result is recorded after execution.

The original-runtime import has returned success with `state: retained` and
`task_completed: true`. A live native retained guard has reopened the typed
proposal and matched the manually prepared result. The returned proposal is
byte-identical to the earlier qualified lineage proposal. The final original-CLI
replay and post-replay claim/control comparisons are still pending; this is not
yet a completed recovery qualification. The first recovery fixture reached these
checks but then called `import-handoff` again on the Retained journal. The CLI
correctly refused with `handoff-reconcile-original-import`; the fixture failed
after 1,383.52 test seconds. This is a harness/API error, not loss of the retained
result. The corrected fixture uses `resume-handoff ... - --apply` for replay.
A separate continuation fixture resumes the existing retained job without return
files, new admission or result generation, then checks claims, journal and controls.
